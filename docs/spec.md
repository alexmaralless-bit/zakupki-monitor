# Монитор госзакупок — спецификация (v0.1, 04.10.2026)

Демонстрационный проект: лидогенератор по тендерам с zakupki.gov.ru. Один пользователь, установка на своём компьютере. Поиск настраивается один раз, дальше система сама собирает закупки в реестр, ставит рейтинг по правилам пользователя и по желанию отправляет выбранные тендеры в CRM через n8n.

**Вне рамок:** логины и роли, многопользовательская работа, облачный хостинг, подача заявок, работа с личным кабинетом ЕИС.

## 1. Сценарий

1. Пользователь создаёт **профиль поиска** (форма или вставка готовой ссылки поиска с сайта).
2. Задаёт **правила «подходит»**: отсев, баллы, при желании — критерий для ИИ обычным текстом.
3. Планировщик по расписанию собирает выдачу → новые закупки попадают в **реестр** с рейтингом и объяснением.
4. Пользователь просматривает реестр, меняет статус, открывает карточку.
5. Кнопка **«В CRM»** отправляет тендер на вебхук n8n; ответ сохраняется.
6. По желанию — сводка новых подходящих тендеров в Telegram.

## 2. Сбор данных

- Источник — страница результатов расширенного поиска ЕИС `https://zakupki.gov.ru/epz/order/extendedsearch/results.html`. Отдаётся готовым HTML, браузер не нужен: **httpx + selectolax**.
- TLS: сайт использует цепочку **Russian Trusted Root CA / Sub CA (Минцифры)**. Сертификаты лежат в проекте (`certs/`), используются только для запросов этого проекта; в систему не устанавливаются.
- Параметры поиска (из ссылки сайта): `searchString`, `morphology`, `fz44`, `fz223`, `af` (подача заявок), `okpd2IdsCodes`/`okpd2Ids`, регион, цена от/до, `sortBy=UPDATE_DATE`, `sortDirection=false`, `recordsPerPage=_50`, `pageNumber`.
- Из выдачи берём на каждую закупку: реестровый номер, закон (44/223), способ закупки, этап, объект закупки, заказчик, начальная цена, даты «размещено / обновлено / окончание подачи», ссылку на карточку.
- **Инкрементальность:** сортировка по дате обновления; обход страниц останавливается, когда на странице нет новых или обновлённых закупок, либо на лимите страниц профиля.
- **Бережность:** 1 поток, пауза 2–4 с между запросами со случайным разбросом, повтор с нарастающей задержкой (3 попытки), честный User-Agent, лимит страниц за прогон.
- **Карточка закупки** (доп. поля: ОКПД2, обеспечение заявки/контракта, место поставки, контакты) — запрашивается только для закупок, прошедших отсев. Документы (ТЗ) — этап 2, только для топа рейтинга.
- Дедупликация по реестровому номеру: повторная встреча обновляет запись (цена, сроки, этап), история изменений — в `tender_events`.

## 3. Правила «подходит» (задаёт пользователь, на профиль)

| Слой | Параметры | Результат |
|---|---|---|
| Отсев | цена от/до; мин. дней до окончания подачи; стоп-слова в объекте; только МСП да/нет; законы | `filtered` + причина |
| Баллы | список правил `{тип, значение, вес}`: слово/фраза в объекте, ОКПД2 (префикс), заказчик (подстрока/ИНН), цена в диапазоне, дней до окончания ≥ N | сумма баллов, нормированная к 0–100, + разбивка |
| ИИ (опц.) | критерий текстом; вес ИИ в итоге (по умолчанию 50 %) | 0–100 + обоснование с **цитатой** из объекта/карточки; без дословной цитаты балл ИИ = 0 |

**Итоговый рейтинг** = `(1 − w) · правила + w · ИИ` (если ИИ выключен — только правила). В карточке показывается разбивка: какие правила сработали, что сказал ИИ и на какую цитату опёрся.

## 4. ИИ

- Провайдер выбирается в настройках: YandexGPT (по умолчанию), GigaChat, OpenAI, локальная модель (OpenAI-совместимый API). Ключи — в `.env`.
- Вызов только для закупок, прошедших отсев; результат кешируется по `(номер закупки, хеш критерия, хеш текста)`.
- Ответ модели — строгий JSON `{score, verdict, reasons[], quotes[]}`, валидация Pydantic; проверка, что каждая цитата дословно есть в тексте.
- Этап 2: краткое содержание ТЗ (3–5 строк) и риски (сроки, обеспечение, СРО/лицензии).

## 5. Реестр (веб-интерфейс)

- FastAPI + Jinja + HTMX, без отдельного фронтенда; доступ только с `127.0.0.1`.
- Таблица: рейтинг, объект, заказчик, цена, окончание подачи (подсветка < 3 дней), закон, профиль, статус. Фильтры, сортировка, поиск по тексту.
- Статусы: `new → interesting / rejected → sent_to_crm`.
- Карточка закупки: все поля, разбивка рейтинга, ссылка на ЕИС, история изменений, кнопка «В CRM», журнал отправок.
- Страницы: профили (создание/редактирование, импорт ссылки), правила, настройки (ИИ, вебхук CRM, Telegram), журнал прогонов.
- Выгрузка в Excel текущей выборки.

## 6. Интеграция с CRM через n8n

- В настройках — URL вебхука n8n (и необязательный секрет в заголовке).
- Отправка: `POST` JSON (схема `tender.v1`):
  `reg_number, law, method, object, customer{name, inn?}, price, currency, published_at, updated_at, deadline_at, url, profile, rating, rating_breakdown, ai{score, verdict, reasons}, user_note`.
- Ответ вебхука `{crm, external_id, url?}` сохраняется; статус → `sent_to_crm`.
- В репозитории — готовые сценарии n8n: **amoCRM** (сделка + компания + задача на дату окончания подачи), **Bitrix24** (то же), **универсальный** (Google Sheets / Telegram).

## 7. Уведомления (опц.)

Telegram-бот: сводка раз в день по новым закупкам с рейтингом ≥ порога + срочные (до окончания подачи < 3 дней).

## 8. Данные (SQLite)

`profiles`, `rules`, `runs` (прогоны: время, страниц, новых, ошибок), `tenders` (уникальный `reg_number`), `tender_events` (изменения), `scores` (по профилю: правила, ИИ, итог, разбивка JSON), `ai_cache`, `crm_exports` (запрос/ответ/статус), `settings`.
SQLAlchemy 2 + Alembic. Файл БД — в `data/`.

## 9. Технологии и качество

Python 3.12, uv, pydantic-settings, httpx, selectolax, SQLAlchemy 2, Alembic, APScheduler, FastAPI, Jinja2, HTMX, openpyxl. Docker / docker-compose — как вариант запуска; основной — `uv run`.
Тесты pytest на **сохранённых страницах** выдачи и карточки (разбор без сети), правила рейтинга, дедупликация, схема `tender.v1`, проверка цитат ИИ (модель — заглушка). ruff, mypy.
